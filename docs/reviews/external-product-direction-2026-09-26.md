# External product perspective: earn the interpretation

26 September 2026. Developer assessment from current code and retained trials, not an independent researcher interview or market study. Proposed direction, not a shipped capability or agreed acceptance protocol.

## Recommendation

Put the hardest decision at the center: **what must be unseen for this experiment to answer its question?** Build toward a researcher comparing plausible independence units against documentation and seeing the measured consequences. The receipt is the record of that decision, not the reason to begin.

The first user is an applied ML graduate student working with repeated observations—audio segments, images, sensor windows—who has experiment partitions and metadata but must decide whether their evaluation addresses unseen observations, recordings, individuals or sites. Frequency, willingness to adopt and time saved remain unknown. Today that person reads documentation and writes a join or asks a coding assistant. Asterisk's available advantage is an inspectable interpretation linked to reproducible measurement; superiority has not been demonstrated.

## Evidence that changes the priority

- The fresh frog trial worked with one model proposal, but the developer selected RecordID before transmission. The system was not tested on discovering the correct scientific identity among competing columns. More runs of that same assisted setup would overstate progress.
- Exact overlap, witnesses, replay, revisions and population-change summaries already exist. Rebuilding those under a new name adds little.
- The frog reassignment correctly refused an empty evaluation partition. An automatic “fixed split” would still need a defensible population and class allocation; zero overlap alone cannot provide that.
- The latest corrective-routing experiment failed and was not integrated. More autonomous retries are not a justified route to reliable interpretation.

## The single product bet

A researcher can reach and explain a defensible independence-unit decision with less preparation using Asterisk than using a general coding assistant, without accepting an unsupported identity interpretation.

The valuable loop is: bring supported metadata and documentation; state what should be unseen; inspect candidate units with quoted definitions and unresolved questions; compare exact overlap under each supported binding; choose the intended unit; export the existing receipt and affected rows for the experiment.

An illustrative screen should distinguish “no shared sample IDs” from “shared recording IDs” rather than presenting the first as a reassuring result. Both are scoped measurements. No candidate is designated a biological individual without documentary support. A zero-overlap candidate is never automatically preferred.

## Build / reuse / skip

| Decision | Component | Reason |
|---|---|---|
| Test before production build | Candidate-unit interpretation and comparison | Directly tests the developer assistance hidden in the successful trial |
| Reuse | Projection, extraction spec, exact checker, witnesses, receipts | Already provide the execution and evidence boundaries |
| Reuse | Existing revision and affected-row exports | Already support acting on a finding, with explicit consequences |
| Skip | Automatic scientifically “optimal” split | Would silently choose a research design |
| Skip | Additional autonomous correction loops | Current evidence does not support their reliability |
| Skip | Universal research claims, model accuracy predictions | Outside measured capability |
| Skip | New dashboard, agents, branding overhaul | Do not test the core bet |

## Proposed bounded test, before implementation

Use six fresh tasks across three nonmedical domains. Retain multiple plausible identifier fields; never project down to the answer before inference. Each task includes a written claim and documentation. Freeze reference bindings and permitted abstentions before execution. Include conflicting documentation, missing identity evidence and an observation-ID trap. Identifiers and documentation must still be reviewed for authorized transmission; broad field retention does not justify uploading personal attributes.

Compare the same inputs with a fresh general coding assistant. Record every preparation action, model call, correction, time and resulting binding. Measure correct interpretation separately from correct arithmetic. Count abstentions on answerable tasks as failures to complete, rather than safety successes. Developer-authored tasks and agent walkthroughs remain development evidence.

Proposed engineering gate: at least five of six correct completed interpretations or correct predeclared abstentions, zero unsupported definitive interpretations, all accepted measurements independently recomputable, and no hidden developer corrections. Evaluate once within 48 hours of approving this protocol; keep failures rather than editing the cases. Passing justifies a comparison UI prototype, not a claim of researcher benefit.

Proposed usefulness gate for that prototype: three target researchers use matched tasks in counterbalanced order; all three can explain the chosen unit and one remaining limitation, at least two complete without developer assistance, and median end-to-end time is lower than the matched assistant workflow. Record setup and correction time. If these thresholds fail, retain the existing manual receipt product and stop expanding preparation. These thresholds are proposed and must be fixed before collecting results.

## Strongest objection

The metadata may not contain enough information to establish the desired unit, and a general assistant may interpret it just as well with less ceremony. Asterisk cannot compensate for absent scientific evidence. Even a reliable comparison feature is not evidence that people want a standalone application.

The immediate missing proof is whether Asterisk can help choose the binding, rather than efficiently process a binding the developer already chose. Spend the next experimental budget there.

## Follow-up: avoid building a duplicate evidence panel

Inspection after the ESC-50 development calls found that the existing preparation review already places identity controls beside editable source evidence, exposes full-file identity counts, and warns that selecting a passage does not verify meaning (`static/preparation-policy.js`). Therefore “show definitions beside choices” is not a missing feature by itself. The proposed comparison direction must earn its place through better decisions or less review effort, not a renamed panel.

The two ESC-50 calls chose the intended binding without column preselection but failed the complete citation requirement in one case. These are development results, not the proposed six-case acceptance run. See `research/identity-choice-preflight/REPORT.md`.

The next useful check is whether a reader can distinguish a schema citation from an identity definition using the existing controls. `research/identity-choice-preflight/READER-TASK.md` provides an unadministered task and separated facilitator rubric. It still needs a provisioned workspace and actual participants. No new comparison UI, automatic approval rule or correction loop is justified by the current evidence alone.
