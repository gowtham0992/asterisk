Different samples. Same subjects?

Training on one image of a specimen and evaluating on another image of the same specimen does not test performance on unseen specimens. Asterisk records an exact-identity overlap check, with the assumptions and evidence needed to inspect it.

Prepare your files

You need realized sample assignments, not the images or model weights. Keep identifiers as text. One CSV can contain all three columns, or you can supply separate tables joined by a sample identifier.

sample_id,partition,patient_id
scan_014,train,P07
scan_092,test,P07
scan_105,test,P12

Include a README or data dictionary explaining what patient_id means and which partition labels represent training and evaluation. These rows are a synthetic example. Do not upload sensitive patient information.

From an existing notebook, export your realized sample IDs, entity IDs and partition labels as CSV. The project also provides asterisk.export_split to export those arrays and a reusable column configuration; see the project README. Asterisk does not execute your notebook to discover a split.

Enable native-file proposals on your installation

A configured Nebius key does not automatically enable native preparation. This separate workflow needs an explicit spending budget and startup switch. If someone else hosts your workspace, ask its operator to configure it. You can still inspect fields locally and use manual CSV setup.

For a new local installation only, run these commands from the project directory after installing its dependencies. Keep your existing NEBIUS_API_KEY in the local .env file. These commands create an estimated $1 preparation budget; they do not call a provider. Do not create a new budget to replace spent, missing, damaged or uncertain accounting from an existing installation.

mkdir -p .data
.venv/bin/python -m app.preparation.init_budget --path "$PWD/.data/preparation-budget.json" --limit-usd 1
export ASTERISK_PREPARATION_BUDGET="$PWD/.data/preparation-budget.json"
export ASTERISK_PREPARATION_NEBIUS=1
sh scripts/start_preview.sh

If the budget already exists, keep it and skip initialization. Stop the previous server before starting the configured process. Reopen preparation: it should say proposals are configured. If startup refuses the configuration, check the credential and existing ledger; do not delete the ledger to make startup succeed. The budget is an estimate, not a billing guarantee. Exact payload review and upload consent are still required for each request.

Sandbox execution is configured separately with the project ID, trusted image and matching driver hash described in the source checkout’s release instructions. Enabling preparation does not enable or authorize a Sandbox run.

Start a split receipt. Supply a CSV split, an identity mapping and documentation. State the generating unit your evaluation should hold out. NVIDIA Nemotron Super reads previews through Nebius Token Factory and proposes the columns and labels. You see cardinalities computed from all rows, correct the fields, and confirm their meaning before execution.

Repeated or blank sample identifiers, identical sample and partition columns, absent labels and conflicting mappings are rejected with specific errors. These are binding checks, not proof that an entity column means “patient” or “specimen.” That assumption remains yours.

What the receipt establishes

After upload authorization, the confirmed arguments go to a trusted checker in Nebius Token Factory Sandboxes. The checker computes overlap and mapping coverage, verifies witness rows, and repeats the same measurement in a fresh Sandbox. A replay mismatch suppresses the verdict.

  • Violation: recorded identities occur on both sides of the confirmed split.
  • Clear: no recorded identity overlaps, coverage is complete, and the exact binding has a recorded confirmation. This is not experiment certification.
  • Insufficient: the available mapping or binding does not establish separation.
  • Incomplete: execution or replay failed; no definitive result is available.

Factual findings and missing-evidence text come from the harness. Any model interpretation is separately labeled unverified. Identity assumptions, undocumented links, duplicate content and accuracy effects are outside the check.

A receipt someone else can inspect

Export the claim, input files, confirmed binding, source quotations, checker source, measured results and replay records. The included verifier checks retained file hashes. Hashes show byte integrity relative to an unsigned manifest; replay shows repeatability. Neither establishes scientific validity or independent provenance. A sender can replace the inputs, checker and manifest together. For a separate check, obtain and verify a matching Asterisk release independently of the receipt, then run python -m asterisk verify /absolute/path/to/receipt from that trusted installation directory. It recomputes with installed code without executing bundled Python or uploading data. It still does not authenticate the author or the original dataset.

Scope and evaluation

Only entity overlap is offered. Checkpoint and preprocessing code remain research artifacts. V3 acceptance failed; v4 is a new development iteration. Human evidence review, comprehension and evidence of reduced verification effort remain unmeasured. A synthetic example or automated confirmation is not a human study.
